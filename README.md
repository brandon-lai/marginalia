# marginalia

A research and reading frontend for the `brain-frontend` vault.

A highlight plus your reaction to it *is* a marginal note, and the PRD's §8
argument is that the reaction is the part worth keeping — a highlight with one
is raw material, a highlight without one is a bookmark. Hence the name.

**The loop:** read something → highlight a passage and say why it matters →
highlights accumulate against one source and one inbox file → when the source is
ready, extract proposed notes → review each one → accept the ones you want, and
the note, the MOC edit, the `index.md` update and the commit all happen at once.

The vault, Obsidian, Quartz and the published site keep working unchanged. This
app is a second consumer of `brain/`, and a producer. The markdown files remain
the only source of truth.

## Running it

**Connecting your own vault for the first time: see [SETUP.md](SETUP.md)** — it
walks through the env file, the database, the Chrome extension, your first
capture-to-commit loop, and how to back any of it out.

```bash
npm install
cp .env.example .env.local     # then edit it
npm run db:init                # applies src/lib/db/schema.sql
npm run dev                    # http://localhost:3117
```

With **nothing configured** it still runs: it serves a bundled synthetic vault
read-only, and every write path refuses loudly rather than pretending. That is
what the public deployment is, and it is what makes a deployment verifiable
before any credential exists.

| Env var | Without it |
|---|---|
| `BRAIN_PATH` | Serves `demo-vault/brain`. No writes, no commits. |
| `BRAIN_REPO` | Defaults to `BRAIN_PATH`'s parent. |
| `DATABASE_URL` | Sources, highlights and proposals are demo rows; writes refuse. |
| `ANTHROPIC_API_KEY` | Extraction returns a pre-written proposal set, labelled as canned. |
| `CAPTURE_SECRET` | `/api/capture` returns 401 to everything. |

`BRAIN_PATH` set to something that is not a vault is a hard startup failure, not
a silent degradation (PRD §11). An *unset* `BRAIN_PATH` is the documented demo
mode; a *wrong* one is a configuration error, and the difference matters because
the alternative is writing notes into the void.

### The Chrome extension

`chrome://extensions` → Developer mode → Load unpacked → `extension/`. Then open
its options and paste the same `CAPTURE_SECRET` value.

`Cmd+Shift+S` saves the selection with the reaction field already focused.
`Cmd+Shift+D` saves the page to read later. Right-click saves a link. If the app
is not running, captures queue in `chrome.storage.local`, the toolbar badge
shows how many are waiting, and they flush every 30 seconds and on browser
startup. A capture is never lost because the server was down.

## Decisions I made, and why

The PRD hands over every open decision. These are the answers this build ships.

### Name

`marginalia`. Short, one word, and it names the actual thesis: the product's
value is the marginal note, not the highlight.

### Supabase vs. Postgres

The PRD specifies Supabase from day one, for four reasons — no SQLite-on-Google-
Drive corruption, no migration when the app is deployed, `pgvector`, and RLS.
All four survive here, because **Supabase is Postgres and the connection string
is the only difference.** The app talks to `DATABASE_URL` via `postgres.js` with
prepared statements disabled and SSL required for hosted URLs, which is exactly
what Supabase's pooler needs. Point it at a Supabase project and nothing else
changes.

Building against local Postgres meant the write path, the schema constraints and
the whole accept pipeline could be verified for real during the build rather
than asserted. `pgvector` is not used yet: §6.5 makes embeddings v1.5 and
keyword matching v1, and the schema leaves room for the column.

### Deployed as a demo, not as your vault

v1 is explicitly local-Mac-only (§2), and the vault is a Google Drive path that
no serverless function can reach. So the deployment runs in demo mode: a
synthetic vault, demo sources, canned extraction, every write refused with a
reason. It is a working demonstration of the product and it is labelled as one
on every screen. It is also literally the first step of M5 — "deploy the same
Next.js app" — so the mobile path starts from a deployment that already works.

**Brandon's actual notes are not in this repo.** The demo vault is generated by
`scripts/seed-demo-vault.mjs` with a seeded PRNG: real structure (subject
folders, MOCs with Topics To Explore, typed `## Connections`, deliberate
unresolved links, an `index.md` subject grid), synthetic content.

### `git` via `child_process`, not `simple-git`

The PRD allows either. A batched `git log` pass was needed anyway for dates, so
`simple-git` would have been a dependency that saved nothing.

### Tailwind plus real CSS

Tailwind v4's `@theme` maps the Quartz palette from `quartz.config.ts` onto
tokens, and `src/app/tokens.css` defines light and dark completely. The
component CSS is hand-written, because the layouts §6 specifies (a highlight and
its reaction as one unit, proposal beside evidence, diff lines) are not utility-
class shaped.

### Push is plain `git push`

Never `npx quartz sync`, which pulls Quartz's upstream `v4` branch into `main`
and drags in unrelated generator changes (system guide §4.3). It is a toggle on
the commit step, defaulted on.

## The open questions, answered

**Q4 — Autonomy level.** *The review gate is mandatory for everything. No
trust-it path in v1.* The word "selective" is the design hinge of the whole PRD,
and the gate is the product. A bypass would be untested autonomy on the one code
path that writes to the irreplaceable asset. What v1 *does* ship is the data
needed to justify a v2 fast path: every proposal records confidence, whether a
reaction backed it, and whether it cleanly matched an open `- [ ]`. When the
`proposals` table shows that high-confidence reaction-backed todo matches are
accepted unedited every time, that is the evidence for relaxing this — and it
will be evidence rather than a guess.

**Q5 — The no-reaction case.** *Process it, mark it low confidence, require an
explicit accept, exclude it from accept-all.* Refusing outright throws away
material already captured, and the user may have had a good reason. Processing
silently is what degrades the vault. So the middle option, made visible: the
server — not the model — sets `noReaction` from the actual highlight rows, caps
confidence below 0.5, and the review card carries a banner saying the framing is
the article's rather than yours. This is the soft gate §8 asks for.

**Q6 — Attachments.** *Text-only; link out.* Three attachments exist today and
adding them freely changes both the character of the vault and the size of a
repo that lives on Google Drive. The reader cache keeps article images available
for *reading* without any of them entering `brain/`.

**Q7 — PDFs.** *v2 for real PDF highlighting.* Anchoring into a PDF is a
different problem from anchoring into HTML and would be most of a milestone on
its own. v1 covers the case at near-zero cost through the manual-paste path that
§6.4 already requires for paywalls: paste the text, get a cached readable
article, highlight it normally.

**Q8 — Existing highlights.** *No import on day one.* No backlog was available
to inspect, so importing would have meant writing a parser for a format I could
not test against. `POST /api/capture` takes the generic payload and is
idempotent per URL, so a Readwise or Pocket export can be replayed through it
later without new code.

**Q9 — The site.** *Quartz stays.* Slug compatibility is replicated verbatim
from `quartz/util/path.ts` and tested against the four cases §11 names. Until
this app is phone-reachable at M5, the published site is the only mobile read
experience — which is the argument the PRD itself makes.

**Q10 — Unverified items.** Still unverified, and neither blocks M0–M3. The
Vercel dashboard build configuration for the *Quartz* project is not readable
from the repo, and this app does not touch it. The Notion books database is
untouched by v1.

## What the tests actually cover

`npm test` — no network, no database, runs against the demo vault by default and
against the real one if `BRAIN_PATH` is set.

- **`[[Byzantine vs. Western Depictions of Christ]]` resolves.** The system
  guide records this as a live data bug: a parser that treats `.` as an
  extension boundary truncates the target to `Byzantine vs`. The character class
  is copied from Quartz's `ofm.ts`, which excludes only `[ ] | # \`. Against the
  real vault the note resolves with 6 backlinks and `Byzantine vs` never appears
  among the unresolved targets.
- **Slugs match Quartz** for all four cases in §11, including the double hyphen
  `&` produces because spaces are converted to hyphens first.
- **A MOC edit leaves every untouched section byte-identical** — verified
  against all 22 real Homebase MOCs, not just fixtures.
- **The todo is removed, not left as a checked box**, and a todo written as a
  wikilink still matches.
- **Highlight anchoring**: prefix/suffix disambiguates a repeated quote,
  `position_hint` breaks ties, re-flowed whitespace survives, an edited tail
  still anchors fuzzily, and an overlapping highlight is reported unanchored
  rather than dropped.
- **Dates are formatted in the commit's own timezone**, because the vault's own
  history has a commit at `23:14 -04:00` that `index.md` records as Jun 04.
- **Recently Added never proposes dropping entries git could not recompute.**

`node scripts/check-contrast.mjs <url>` composites all four highlight colours
against the real page background in both themes and fails below 4.5:1.

### Verified end to end, against a clone of the real vault

Run against a git clone of the actual `brain-frontend` repo with a real Postgres
database (never against the Drive original):

- 231 notes indexed, zero basename collisions, folder counts matching the
  system guide exactly.
- An unauthenticated capture returns 401; a wrong secret returns 401.
- Two highlights from the same URL append to **one** inbox file, blockquoted,
  with `draft: true`.
- An external writer (Obsidian) appending to that file mid-flight loses
  nothing, and neither does the capture that arrives after it.
- Accepting a proposal wrote `System Design/Distributed Tracing.md`, inserted
  one line into the System Design MOC leaving all ten other sections
  byte-identical, rewrote `Recently Added`, and committed all four files.
- `Distributed Tracing` — a genuine unresolved link in the real vault — now
  resolves with 3 backlinks, and the note introduces one *new* deliberate
  unresolved link (`Observability`), which is the write-next queue working as
  designed.
- Duplicate basenames, folder-qualified wikilinks and frontmatter on a permanent
  note are each rejected with a specific message before anything is written.

## Layout

```
src/lib/vault/     slug.ts  wikilink.ts  parse.ts  index.ts  store.ts
                   moc.ts   indexmd.ts   inbox.ts  git.ts
src/lib/db/        client.ts  repo.ts  schema.sql  demo-data.ts
src/lib/extract/   prompt.ts  anthropic.ts  context.ts  demo.ts
src/lib/reader/    extract.ts  anchor.ts  cache.ts
src/lib/commit.ts  the six protocol side effects, behind one Accept
extension/         Chrome MV3: popover, offline queue, options
demo-vault/        generated; synthetic content, real structure
```

`VaultStore` (`src/lib/vault/store.ts`) is the seam §3.4 asks for: `list`,
`read`, `write`, `delete`, `commit`. Swapping `FsVaultStore` for a GitHub
Contents API implementation is what M5 needs, and nothing above the interface
changes. `Extractor` (`src/lib/extract/types.ts`) is the same seam for the
model.

## Invariants the code enforces

Checked in `validate()` before any write, and refused with a reason rather than
half-applied:

1. Basenames stay globally unique.
2. Wikilinks are bare basenames — never `[[Computer Science/Big O]]`.
3. H1 equals the filename stem.
4. No frontmatter on permanent notes. Inbox captures only.
5. Concurrent writers assumed: read-before-write, hash compare, write to a temp
   file in the same directory and `rename()`. A partial write on Google Drive is
   a corrupted note.
6. Structured edits to MOCs, never regex over the whole file.
